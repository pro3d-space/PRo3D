# CLAUDE.md

## Repository overview
PRo3D (Planetary Robotics 3D Viewer) — interactive 3D surface reconstruction 
viewer for planetary science. Built on the Aardvark platform (F#, .NET 9).

## Module map
- `PRo3D.Base`              — core domain types, annotation model, serialization,
                              coordinate transforms (CooTransformation), utilities
- `PRo3D.Core`              — app logic: drawing, groups, surfaces, bookmarks,
                              scale bars, GIS, reference systems, sequenced bookmarks
- `PRo3D.Viewer`            — top-level viewer app; Viewer.fs is the main update loop
- `PRo3D.CorrelationPanels` — stratigraphic correlation panel subsystem (large,
                              self-contained)
- `PRo3D.SimulatedViews`    — rover viewplanning, snapshots, lighting simulation
- `PRo3D.GIS`               — GeoTIFF, projected images, celestial body support
- `PRo3D.Lite`              — lightweight viewer variant
- `PRo3D.Snapshots`         — headless snapshot generation (no interactive UI)
- `Tests`                   — existing test project; use this for new tests

## Code generation (Adaptify)
Files named `*.g.fs` are auto-generated by Adaptify from their `*-Model.fs`
counterpart. Never edit `.g.fs` files directly — edit the model and regenerate.

The correct regeneration command (required flags, run from repo root):
```
dotnet adaptify --lenses --local --force src\<Project>\<Project>.fsproj
```
- `--lenses` generates the Aether lens static members (`field_`) that ViewerLenses.fs
  and other files depend on — omitting it produces a truncated file that breaks the build
- `--local` writes the result back to the source `.g.fs` file (not just `obj/`)
- `--force` bypasses the cache and always regenerates

`adapt.cmd` in a project directory and `RunAdaptify.fsx` both invoke this correctly.
Running `dotnet tool run adaptify` without these flags will silently produce an
incomplete `.g.fs` and cause many downstream `error FS0039` lens errors.

## Testing strategy
- Test project: `src/Tests/Tests.fsproj`
- Existing tests: BaseTests.fs, GeoJsonExportTest.fs, HeraSpiceTests.fs,
  QueriesDSL.fs
- Test data: `src/Tests/Annotations/`, `src/Tests/data/`
- Architecture is MVU: update functions are pure `Message -> Model -> Model` —
  test by calling update directly, no running instance needed
- Pattern: construct model state → apply message(s) → assert model fields
- Use Expecto (already in project) for test structure
- Use FsCheck for property-based tests over message sequences
- `PRo3D.Snapshots` runs headless — its initialization path may be reusable
  for constructing real model state in tests without building it by hand

## What NOT to test
- Anything in `*.Sg.fs` files (scene graph, rendering)
- Anything requiring an OpenGL context
- `.g.fs` generated files
- Aardvark adaptive/incremental values (aval, alist, aset) — verify by build

## F# conventions
- Discriminated unions preferred over enums for domain types
- Pipeline operator `|>` over nested calls
- `*-Model.fs` = type definitions; `*App.fs` = update + UI logic — respect
  this separation when adding code
- Never add mutable state outside of Aardvark transactions
- Don't use C#-style patterns (classes with properties, imperative loops)

## Aardvark-specific patterns
- `update` may return `model * Cmd<Message>` in some apps — ignore Cmd in
  tests, assert only the model component
- `plist`, `hmap`, `alist` are Aardvark persistent collections — use their
  module functions, not .NET BCL equivalents
- Lenses (`Lenses.fs`) are generated — use them for model updates in app code

## Workflow
- Always create a feature branch before changes
- Build before committing — F# type errors are the primary feedback loop
- When modifying a `*-Model.fs`, run adaptify to regenerate the `.g.fs`
- For new domain features: add types to the appropriate `*-Model.fs` first,
  then update functions, then UI last
